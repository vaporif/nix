Why a setup at all

A bare agent gets in its own way

  • It edits the checkout you're working in. Two tasks can't run side by side.
  • It asks permission constantly, so you end up sitting and watching it.
  • It forgets everything when the context window fills or the session ends.
  • It codes before it thinks, and the bad assumptions only show up in review.
  • It leaves AI slop: narrating comments, extra abstractions, dead code.

What this setup changes

  • Each issue gets its own worktree
  • A sandbox and guard hooks replace permission prompts
  • You get a spec and a plan before any code
  • Review and polish run as a pipeline
  • Decisions are kept in memory across sessions

Why not install everything globally?

Every agent, rule and MCP tool you install globally costs prompt tokens in every session, including projects where it can never apply.

Scoping them to the project keeps the context for the actual work, and the agent doesn't get Solana advice while fixing a Lua plugin.

2 · Isolate

Let it run unattended, with a sandbox around it

sandbox

bubblewrap on Linux: read-only /nix, selected /etc, only the project and cache dirs writable. The real protection.

bash guard

A PreToolUse hook parses every shell command. It hard-denies git push, reset --hard, git clean and curl-pipe-to-shell, and asks on sudo, rm and dd. It's tested against 38 bypass payloads.

deny list

Read/Edit blocked on secrets, keys and credential dirs.

ask list

Named risky tools prompt with a human-readable reason.

$ a # sandboxed claude, # no permission prompts › throw away my changes and push ⏺ Bash(git reset --hard) ✗ denied by hook ⏺ Bash(git push) ✗ denied by hook pushing stays with you.

3 · Design

A spec comes before any code

brainstormAsks questions one at a time and proposes options with pros and cons for each.
→
specdocs/specs/2026-09-30-empty-input-design.md
→
/spec-reviewTwo finders: doc quality and checked against the codebase, with file:line evidence.
→
verifyOne verifier per finding. Findings that don't hold up are dropped.
→
fix or parkIf a fix has no downside it's applied. Real trade-offs are parked for you.

It runs up to 3 rounds. You only see the decisions that are actually yours to make, and false assumptions about the code get caught before any code is written.

5 · Build

Subagents build it and review each other

per task

Fresh context each time

Each task goes to a new subagent with only the plan and the spec. The main session stays small and in charge.

discipline

Test first

A failing test, then the code. "Done" means a command ran and passed, not that the agent says so.

when stuck

Debug by hypothesis

Systematic debugging: root cause before any fix. For hard bugs, several agents each investigate a competing theory.

Every task is reviewed before the next batch starts. The same shared commands, rules and agents are used by Claude and Codex.

8 · Ship

Commit, PR, and the MR discussion in one place

› /commit fix(parser): handle empty input confirm? y › /pr reads the branch log + diff, follows the repo's PR template $ git wr fix/42-empty-input worktree removed, branch deleted (kept if unmerged)
  • /commit writes one conventional line and waits for your confirm.
  • /pr writes the title and description from the whole branch, not only the last commit.
  • At work (GitLab): review threads, line comments, suggestions, approvals and pipeline status all inside Neovim (␣cvr, ␣cvc, ␣cva, ␣cvp).

9 · Remember

The next issue starts with what this one taught

/remember

Store it

Facts as triples (parser · returns · Option), events as episodes, workflows as procedures. Stored per project, tagged with entities.

/docs

Update the docs

Updates CLAUDE.md, auto-memory and ferrex from the branch diff, so the next agent reads the new convention.

/reflect

Keep it true

Finds stale and contradictory memories. You /forget or replace them.

Backed by a local vector DB (qdrant). Nothing leaves the machine.
